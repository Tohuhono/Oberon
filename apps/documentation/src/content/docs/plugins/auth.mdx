# Authentication and authorization

OberonCMS uses Better Auth for email codes and sessions. Automatic signup is disabled. Users must
exist in the CMS before they can sign in.

## Setup

Add `authPlugin` from `@oberoncms/core/auth` to your server config. Put it after the database, send,
and framework plugins. See [Configuration](/docs/configuration) for an example.

The auth plugin needs these Adapter capabilities:

- `getAuthDatabase` and `getAuthPlugins` for Better Auth storage and extensions
- `sendVerificationRequest` for email delivery
- `getRequestHeaders` for request sessions

The database and framework plugins supply the required auth capabilities. See
[Database](/docs/plugins/database) and [Send](/docs/plugins/send) for provider setup. Mount the
[framework HTTP handler](/docs/plugins/custom/handler-hooks) at `/cms/api/`.

## Environment variables

```sh
MASTER_EMAIL=admin@example.com
AUTH_SECRET=your-generated-secret
BETTER_AUTH_URL=https://your-site.example
EMAIL_FROM=noreply@example.com
```

The installer generates `AUTH_SECRET`. Keep it private and stable across deployments. The auth
plugin uses `BETTER_AUTH_URL`, then `VERCEL_URL`, then `BASE_URL` to select its base URL.
`OBERON_SITE_URL` does not configure the current auth plugin. Set the credentials required by your
email provider separately.

## Initial admin

Bootstrap creates an `admin` user for `MASTER_EMAIL` if that email does not exist. It does not
change an existing user's role. This variable is not an emergency permission override. Use a secure
mailbox for the initial admin.

## Sign-in

1. Open `/cms/login`.
2. Enter an existing user's email.
3. Request a sign-in code.
4. Enter the code or open the email link.

The development plugin writes verification details to the terminal instead of sending email.
Production needs a configured [send plugin](/docs/plugins/send).

## Permissions

The default roles are `admin` and `user`. Admins can manage all CMS resources. Users can edit pages
and images and read Site information. Unauthenticated requests can read pages.

CMS actions use `can`, `will`, and `whoWill` to enforce permissions. Persistence methods do not
enforce these permissions themselves. Custom HTTP handlers must check access before they expose
protected data or mutations.
